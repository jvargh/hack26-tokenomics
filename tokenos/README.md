# TokenOS — AI Workflow Optimizer

Real input, real local analysis, optional Microsoft Foundry model execution, and measured proof
across the seven TokenOS phases.

The fourth workflow is **Optimize an existing AI workflow**. Start with the
[evaluator walkthrough](samples/OPTIMIZATION-WALKTHROUGH.md) for its explicit
Describe, Plan, Optimize, Protect, Run, Verify, and Prove journey. Analyze-only
telemetry, measured governed execution, and a paid matched baseline are separate
actions with different claim strength.

See [optimization API and local Foundry configuration](services/tokenos-api/OPTIMIZATION-API.md)
for request shapes, immutable Protect contracts, registered scopes, pricing, and
explicit limitations. The optimization UI never handles provider credentials.

Working on the code itself? Read the [engine deep dive](ENGINE-DEEP-DIVE.md) — control flow,
invariants, extension recipes, and where every rule lives.

Evaluating the product's value? Read [why TokenOS is essential to tokenomics](TOKENOS-BENEFITS.md) —
seven benefits, each backed by the mechanism that enforces it.

```
tokenos/
  apps/web/               React + Vite + TypeScript UI
  services/tokenos-api/   FastAPI service: uploads, plans, execution, events, proof
  samples/                Sample provenance notes (data is generated by the API)
```

## Run it

Two terminals.

```powershell
# Terminal 1: local TokenOS API
Set-Location tokenos\services\tokenos-api
py -3.13 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn tokenos_api.main:app --host 127.0.0.1 --port 8000
```

```powershell
# Terminal 2: UI
Set-Location tokenos\apps\web
npm install
npm run dev            # http://localhost:5173
```

API docs: `http://localhost:8000/docs`. Health: `http://localhost:8000/health`.

With no Foundry configuration the API runs in **local mode**: every workflow still executes for
real, and operations that would need a model report that no deployment is configured instead of
producing invented output.

### Presentation pacing

Real analysis finishes in tens of milliseconds, which is far too fast to watch. The server inserts
small delays *between emitted events* so the seven phases and each operation are observable. These
delays never touch the numbers: measured work time in the proof subtracts all pacing, and each
operation's duration is measured around the real handler call.

| Variable | Default | Effect |
| --- | ---: | --- |
| `TOKENOS_PHASE_PACING_MS` | 500 | Pause before each phase transition |
| `TOKENOS_OPERATION_PACING_MS` | 240 | Pause before each operation executes |
| `TOKENOS_STEP_PACING_MS` | 90 | Pause between route selections and protection checks |
| `TOKENOS_STREAM_ATTACH_TIMEOUT_SECONDS` | 3.0 | How long a run waits for the browser to attach before streaming |

Set all three pacing values to `0` for automated clients:

```powershell
$env:TOKENOS_PHASE_PACING_MS = "0"; $env:TOKENOS_OPERATION_PACING_MS = "0"; $env:TOKENOS_STEP_PACING_MS = "0"
```

### Microsoft Foundry (hybrid routing)

The local API stays the control plane. It decides whether a model is needed at all,
checks policy and budget, records usage, and validates the result. Foundry only
supplies reasoning that regular software cannot complete.

Use the helper script, which sets the verified values:

```powershell
az login
python -m pip install openai azure-identity
.\services\tokenos-api\start-foundry.ps1
```

Or set them yourself:

```powershell
$env:TOKENOS_MODEL_MODE = "foundry"
$env:TOKENOS_FOUNDRY_BASE_URL = "https://<resource>.openai.azure.com/openai/v1/"
$env:TOKENOS_FOUNDRY_EFFICIENT_DEPLOYMENT = "<efficient deployment>"
$env:TOKENOS_FOUNDRY_ADVANCED_DEPLOYMENT = "<advanced deployment>"
$env:TOKENOS_FOUNDRY_AUTH_MODE = "entra"
```

Confirm with `GET /health`, which should report `"foundryAvailable": true` and both
deployment names.

**Authentication.** Entra ID is the default and is required when the account has
`disableLocalAuth: true`. The signed-in principal needs the **Cognitive Services
OpenAI User** role on the account:

```powershell
az role assignment create --assignee <upn-or-object-id> `
  --role "Cognitive Services OpenAI User" `
  --scope "/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.CognitiveServices/accounts/<account>"
```

The token audience defaults to `https://cognitiveservices.azure.com/.default`, which
is correct for both Azure OpenAI and AI Services accounts. Override with
`TOKENOS_FOUNDRY_TOKEN_SCOPE` only for a different resource type.

Populate `services/tokenos-api/price_table.json` with the prices for your deployments,
keyed by **deployment name** and versioned by model, model version, region, and
effective date. Until it is populated, the UI reports *Measured usage, price table not
configured* rather than a made-up cost.

## The four workflows

Each one collects different real input and runs different local analysis.

| Workflow | Required input | What actually happens | Model calls |
| --- | --- | --- | ---: |
| Review documents against rules | Documents + policy/rules + review focus | Text extraction, SHA-256 duplicate detection, Markdown-table charge parsing, section-aware rule reading (dollar limits, percentage caps, approval requirements, duplicate rules), per-line approval evidence, repeated charge-line detection, citation and amount verification | 0–2 |
| Test a code change | ZIP/diff/OpenAPI + requested change | Path-traversal checks, file inventory, OpenAPI parsing, schema-mismatch detection, secret scan, allow-listed `python -m unittest` in a temp directory with a 10s timeout | 0–2 |
| Process records by a deadline | CSV/JSON dataset + instruction + deadline | Full local parse, real record count, invalid-row reporting, measured throughput, deadline route selection, rule-based classification | 0–1 |
| Optimize an existing AI workflow | Normalized telemetry and/or 3-20 representative requests | Local planning, independently evaluated optimization levers, explicit Protect authorization, measured execution, outcome verification, optional matched all-AI baseline | Conditional |

The first three existing API IDs remain `document_review`, `software_validation`, and
`deadline_processing`. The specification calls the latter two `validate_software` and
`meet_deadline`; their existing persisted IDs are deliberately not renamed.
The new fourth selection is `workflow_optimization`. The legacy `false_savings` API and
economics remain available for compatibility, but are no longer a primary selection.

Historical local-mode measurements for the original engines (not measurements of the
new optimization workflow). See the implementation report for current validation:

| Workflow | Result | Measured work |
| --- | --- | ---: |
| Legacy route-economics analysis (`false_savings`) | False saving detected, 0 model calls | ~40 ms |
| Review documents against rules | 2 findings: 2 charges over their applicable limit | ~35 ms |
| Test a code change | 3 tests run, 1 failed, 1 schema mismatch, reported honestly | ~220 ms |
| Process records by a deadline | 9,989 valid records processed, 11 invalid reported, deadline met | ~110 ms |

## Token economics

This is the point of the product. The workload — invoices, code, records — is only a
controlled way to prove the routing decision. The optimization Prove screen leads with outcome quality, route decisions, and measured
economics. Technical evidence stays collapsed until requested.

### What is measured, and what is not

| Number | How it is produced |
| --- | --- |
| Cost of this run | Tokens reported by the model response × the configured price |
| If every step used AI | tiktoken count of the text each operation read and produced × price |
| Cost difference | The two above, subtracted |
| Verified saving | Only after `POST /api/runs/{id}/baseline` executes the all-AI path *and* both paths pass the same checks |

The projection uses exact token counts of real text. Only the routing is hypothetical,
so it is labelled a **cost difference**, never a saving. `saving_claimable` stays `false`
until a paired run exists. Claiming a saving from a projection would be the same false
economy this product exists to expose.

### The routing ladder

`document_review` plans eight operations:

| Route | Operations | Why |
| --- | --: | --- |
| Regular software | 5 | Hashing, duplicate detection, charge extraction, rule evaluation, citation checks — zero tokens |
| Approved retrieval | 1 | Reads the supplied policy directly |
| Efficient model | 1 | Writes the decision summary from already-verified findings |
| Advanced model | 1 | Reserved for ambiguity that survived every cheaper route |

The bundled sample contains one charge (`Rework of previously delivered items`) whose
governing section explicitly defers to judgement. Rules cannot settle it, so it escalates.
With no deployment configured, TokenOS reports it **unresolved** rather than answering it —
the routing decision stays visible instead of being silently downgraded.

### Turning the projection into a proof

```powershell
$env:TOKENOS_MODEL_MODE = "foundry"
$env:TOKENOS_FOUNDRY_BASE_URL = "https://<resource>.openai.azure.com/openai/v1"
$env:TOKENOS_FOUNDRY_ADVANCED_DEPLOYMENT = "<deployment>"
```

Then check the acknowledgement box and press **Run the all-AI comparison** on the Prove
screen. The button stays disabled until you confirm you understand the run may spend real
model cost — the API itself refuses `POST /api/runs/{id}/baseline` with a `400` unless the
request body carries `{"acknowledged": true}`, so no client can trigger spend silently. It
then sends the same documents to the advanced model, measures real tokens and cost, and
applies the *same* grounding, amount, and citation checks used by the governed run. A
saving is labelled **verified** only when both paths pass and the baseline actually costs
more; if the baseline costs the same or less, or either path fails its quality checks,
TokenOS reports **no saving** or **invalid comparison** instead — see
`baseline.evaluate_saving` in `services/tokenos-api/tokenos_api/baseline.py`.

### Prices

`price_table.json` ships with public list prices for a gpt-4o-mini class and gpt-4o class
deployment, with an effective date and source. **Confirm them against your own agreement
before treating any figure as your real cost.** Setting `effective_date` to `""` makes
TokenOS report tokens with no calculated cost.

## Policy rules the document reviewer understands

Rules are read from the supplied policy, never hard-coded. Each is an exact check, so no
model is needed to apply them:

| Rule kind | Recognised from | Applied as |
| --- | --- | --- |
| Dollar limit | "maximum of $500.00", "not exceed $150" | Charge amount compared with the limit |
| Percentage cap | "does not exceed the published monthly cap of 8.0%" | Percentage stated on the charge line compared with the cap |
| Approval required | "payable only when…approval", "not payable unless…approval" | Charge row must carry an approval identifier such as `AP-9465` |
| Duplicate prohibited | "duplicate", "repeats the same…previously invoiced" | Repeated reference plus amount within a document, and duplicate documents by digest |
| Requires interpretation | "requires interpretation", "where responsibility is contested" | Escalated to a model — the one path on which a model may act |
| Payable condition | "are payable when…" | Marks the charge as governed, so it is not reported as unexplained |

Rules are matched to charges by policy section, with heading words weighted above body
words. A rule written about "any charge" or "all invoices" applies to charges no section
names. `not payable unless` is treated as a rejection; `payable only when` asks for
evidence instead. Approval evidence is read from the charge's own row, so a note reading
"No approval ID is listed" is correctly treated as missing rather than present.

If a charge matches no rule at all it is reported as unmatched and the rule-coverage check
fails — the reviewer never reports a clean result it did not actually establish.


- **Upload my data** — files go to `POST /api/uploads`, are validated and text-extracted server-side,
  and are referenced by server-issued upload IDs.
- **Use a connected application** — a registered TokenOS integration identified by application and
  reference. The browser sends only those two names; the server decides what the application is
  permitted to return. It does not connect TokenOS to an Azure subscription, and no provider
  credentials reach the browser.
- **Use sample data** — bundled input pushed through the *same* upload, extraction, and analysis
  path. Results are labelled **Measured sample run**, never Simulated.

### Registered applications

`tokenos_api/connectors.py` holds the registry. Every connector shipped today is a **local stub**
that returns bundled records, so the connected path can be exercised without external credentials.
Those runs are labelled **Measured run, local connector stub** and the UI says so, so a stub result
is never mistaken for a live system of record.

| Application | Workflow | Reference | Returns |
| --- | --- | --- | --- |
| Claims Assistant | Review documents against rules | `wf-4821` | Freight invoice (5 charges) + freight policy |
| Vendor Desk | Review documents against rules | `case-7702` | Contractor invoice (4 charges) + contractor policy |

An unknown application, an unknown reference, or an application registered for a different
workflow is refused with a message naming what *is* available. Workflows with no registered
application say so plainly instead of showing an empty picker.

To add a real connector, add a `ConnectedApplication` whose adapter fetches from the live system
and set `connection_kind` accordingly; nothing in the UI or runner needs to change.

## API

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/health` | Service, model mode, and Foundry availability |
| `GET` | `/api/workflows` | Workflow definitions and input schemas |
| `POST` | `/api/uploads` | Upload and validate real files |
| `POST` | `/api/uploads/sample` | Materialize bundled samples through the upload pipeline |
| `GET` | `/api/connections` | Registered applications for a workflow, with scope and references |
| `DELETE` | `/api/uploads/{id}` | Remove an unused upload |
| `POST` | `/api/runs/analyze` | Validate inputs and compile a real plan |
| `POST` | `/api/runs` | Start an approved run (idempotency key honoured) |
| `GET` | `/api/runs/{id}/events` | SSE stream with `Last-Event-ID` replay |
| `GET` | `/api/runs/{id}` | Authoritative run state for recovery |
| `POST` | `/api/runs/{id}/approve` | Record a human approval decision |
| `POST` | `/api/runs/{id}/stop` | Stop new work safely |
| `GET` | `/api/runs/{id}/proof` | Final measured proof, including token economics |
| `POST` | `/api/runs/{id}/baseline` | Execute the all-AI path and verify it the same way. Requires `{"acknowledged": true}` — refuses with `400` otherwise, so no model spend is ever triggered silently |
| `GET` | `/api/runs/{id}/comparison` | Read-only: the cached baseline/comparison result, or `{"status": "not_requested"}`. Never triggers a model call |
| `GET` | `/api/runs` | Run history |
| `GET` | `/api/reports/runs` | Durable ledger report across every completed run and baseline (see below) |

Full request/response examples for every endpoint above, including the acknowledgement
gate and the comparison lifecycle, are in
[services/tokenos-api/API.md](services/tokenos-api/API.md).

### Durable run ledger

Every proof and baseline is written to a small SQLite ledger
(`services/tokenos-api/tokenos_api/storage/ledger.py`, file configurable via
`TOKENOS_STORAGE_ROOT`) independent of the in-memory run state used for live SSE. This is
what `GET /api/reports/runs` reads from, so a saving claim, a route count, or a measured
cost can be audited after the fact — even after the process restarts — not just observed
live in the browser. A run is only ever recorded once its proof or baseline actually
finishes; nothing is written speculatively.

## Rules enforced in code

- No browser timer creates phase, cost, token, quality, or savings results. Every phase change comes
  from a server event, and a run waits for the browser to attach before streaming so no phase is
  skipped.
- Presentation pacing lives on the server and is excluded from measured work time.
- Uploaded files are represented by server-issued IDs; the original filename is never used as a
  storage path, and archives are rejected on path traversal.
- Foundry is called only by the server. Advanced AI is conditional, never automatic.
- Costs come from measured token usage and an administrator-configured price table.
- Avoided cost appears only when the server produced a valid measured baseline.
- Failed or quality-rejected outcomes are never counted as savings.
- A dropped event stream recovers from `GET /api/runs/{id}` instead of restarting the run.
- Starting another run clears the workspace, files, and metrics, but never deletes a recorded proof.

## Tests

There are two independent test suites: an automated, credential-free `pytest` suite that
runs in-process, and a handful of manual scripts that exercise a live server (optionally
with real Foundry credentials).

### Automated suite (`pytest`)

No running server, no credentials, no network. `tests/conftest.py` forces
`TOKENOS_MODEL_MODE=local` and a scratch `TOKENOS_STORAGE_ROOT` **before** `tokenos_api` is
imported, so it always overrides a `foundry`-configured `.env` and never writes into the
real runtime ledger.

```powershell
Set-Location tokenos\services\tokenos-api
python -m pip install -r requirements.txt -r requirements-dev.txt
python -m pytest -v          # ~80s, 36 tests
```

Covers, using a real in-process `TestClient` driving actual workflow execution end to end:

- `test_pricing_unit.py` — price lookup, cost calculation, and "not configured" handling
- `test_savings_eligibility.py` — every branch of `baseline.evaluate_saving`: eligible
  saving, no-saving at equal/lower baseline cost, and each invalid-comparison reason
- `test_ledger_unit.py` — the durable SQLite ledger: persistence, idempotency, join between
  a run and its baseline, and summary aggregation
- `test_comparison_endpoint.py` — the acknowledgement gate on `POST /baseline` (400 without
  it, 200 with it), and that `GET /comparison` round-trips and never itself spends
- `test_route_counts.py` — route/model-call/cost counts reconcile across `routing`,
  `usage`, and per-operation `detail` for every one of the four workflows, and that
  `document_review`'s summary step never silently routes to a model
- `test_foundry_unavailable.py` — with no deployment configured, `/health` and
  `/api/workflows` report it plainly, `document_review` still completes with unresolved
  items instead of inventing an answer, and `/baseline` refuses to spend

### Manual / live verification scripts

These need the API already running (`tests/test_workflows_live.py`,
`tests/test_full_matrix.py`) and, for a real all-AI comparison, a configured Foundry
deployment (`tests/check_prove_numbers.py`). They expose no `pytest` test functions — each
has its own `if __name__ == "__main__":` entry point — so `pytest` safely imports and skips
them (see `pytest.ini`).

```powershell
Set-Location tokenos\services\tokenos-api
python tests\test_workflows_live.py   # smoke: all four workflows complete
python tests\test_full_matrix.py      # full matrix: 74 assertions, ~90s
python tests\check_prove_numbers.py   # live Foundry: inspect a real governed run + baseline
```

`test_full_matrix.py` covers every workflow against every input source and asserts the
**findings** and **reviewed items** against values derived by hand from the inputs — not
just that a run completed. It checks, among other things:

- each rule kind is enforced: dollar limit, percentage cap, approval required, duplicate line
- the reviewed table and the findings list never disagree about the same charge
- withheld and payable totals reconcile against the sum of reviewed charges
- a failing test is reported as `completed_with_findings`, never as a pass
- an unknown application, unknown reference, or wrong-workflow application is refused with a
  message naming what is available
- `reviewed_items` is `[]` for non-document workflows rather than a half-built list

Speed the suites up by disabling presentation pacing:

```powershell
$env:TOKENOS_PHASE_PACING_MS = "0"
$env:TOKENOS_OPERATION_PACING_MS = "0"
$env:TOKENOS_STEP_PACING_MS = "0"
```
